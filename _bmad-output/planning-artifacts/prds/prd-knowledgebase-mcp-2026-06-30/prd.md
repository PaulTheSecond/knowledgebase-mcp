# PRD: Autonomous Sync & Dashboard Module (v1.3 - v1.6)

## 0. Назначение документа

Этот документ определяет требования к системе автономной фоновой синхронизации, механизмам проверки подлинности входящих триггеров (вебхуков), безопасному хранению учетных данных и панели визуального мониторинга (Web UI Dashboard) для проекта `knowledge-mcp`. 

Документ предназначен для команды разработки (для реализации функционала) и системных архитекторов (для контроля качества проектных решений). Данный PRD основывается на предварительной спецификации [spec_autonomous_sync.md](file:///c:/Repos/knowledgebase-mcp/docs/spec_autonomous_sync.md) и архитектурных решениях [ADR-004](file:///c:/Repos/knowledgebase-mcp/docs/adr-004-autonomous-sync-triggers-credentials.md) и [ADR-005](file:///c:/Repos/knowledgebase-mcp/docs/adr-005-web-dashboard-architecture.md).

## 1. Видение (Vision)

В текущей версии `knowledge-mcp` (v1.2) синхронизация базы знаний с кодом репозиториев требует ручных команд разработчика, что приводит к рассинхронизации локального контекста и ошибкам в работе ИИ-ассистента Codex.

Цель этого обновления — превратить базу знаний в автономную систему, которая автоматически поддерживает свою актуальность на основе событий Git-сервера. Разработчики просто фиксируют свои коммиты, а контейнер `knowledge-mcp` безопасно вытягивает дельту изменений через SSH/PAT, запускает инкрементальный парсинг AST и векторизацию контекста.

Пользователи получают веб-интерфейс (Dashboard) для визуального контроля состояния базы знаний, просмотра надежной БД-очереди задач синхронизации и встроенный RAG-чат для оперативного тестирования семантического поиска и получения ответов от локально подключенных моделей (через прокси `omniroute`).

## 2. Персонажи и пользовательские сценарии (User Journeys)

### 2.1. Jobs To Be Done (Задачи пользователей)
* **Как разработчик**, я хочу, чтобы мой ИИ-ассистент в IDE всегда обладал актуальным контекстом проекта, не требуя от меня ручного запуска команд синхронизации.
* **Как лид команды**, я хочу иметь веб-интерфейс для контроля качества индексации, просмотра накопившихся задач в очереди и быстрого разбора ошибок парсинга кода.
* **Как разработчик**, я хочу иметь возможность прямо из браузера протестировать семантический поиск по всей кодовой базе в режиме чата, используя мощные локальные модели.

### 2.2. Пользовательские сценарии (Journeys)

* **UJ-1. Алексей видит авто-обновление базы знаний после пуша**
  * **Контекст:** Алексей (старший разработчик) делает пуш в ветку `main` репозитория `Yurta.Core.Lib`.
  * **Входное состояние:** MCP-сервер запущен, настроены доступы.
  * **Путь:**
    1. Алексей отправляет изменения: `git push origin main`.
    2. Git-сервер отсылает вебхук на `/webhook/git`.
    3. Валидатор вебхуков подтверждает подлинность HMAC-подписи и помещает задачу в БД-очередь.
    4. Фоновый воркер забирает задачу по FIFO, выполняет инкрементальное обновление кэша исходников в `/data/clones/Yurta.Core.Lib` и обновляет SQLite-базу.
  * **Кульминация:** Алексей задает ассистенту Codex вопрос по новому API в IDE и получает точный ответ со ссылкой на только что запушенные строки.
  * **Резолюция:** База знаний обновилась в фоне, система перешла в режим ожидания.

* **UJ-2. Иван настраивает и тестирует приватный репозиторий**
  * **Контекст:** Иван (DevOps) настраивает интеграцию с приватным Git-репозиторием.
  * **Входное состояние:** Иван открыл Web UI Dashboard, авторизовался.
  * **Путь:**
    1. Иван нажимает "Add Repository", указывает Git URL и выбирает тип авторизации "SSH".
    2. Указывает путь к примонтированному ключу в контейнере.
    3. Нажимает "Sync Now". Бэкенд создает запись в очереди задач.
  * **Кульминация:** Иван видит в реальном времени появление задачи в таблице очереди и успешный процесс первой индексации репозитория.
  * **Резолюция:** Статус репозитория переводится в `Active`.

* **UJ-3. Мария обращается к встроенному RAG-чату**
  * **Контекст:** Мария (фронтенд-разработчик) ищет примеры использования API уведомлений в бэкенд-репозиториях.
  * **Входное состояние:** Мария открыла вкладку "RAG Chat" в веб-панели.
  * **Путь:**
    1. Мария пишет запрос: *"Как вызвать NotificationService.Send?"*.
    2. Бэкенд запрашивает гибридный поиск по базе, собирает топ-5 кусков кода.
    3. Бэкенд отправляет промпт через локальный прокси `omniroute` в модель `kr/claude-sonnet-4.5`.
  * **Кульминация:** Ответ выводится на экран посимвольно (стриминг) с красивой подсветкой кода и списком файлов-источников с номерами строк.
  * **Резолюция:** Мария получает ответ и переходит по ссылке к файлу-источнику.

## 3. Глоссарий (Glossary)

* **Локальный кэш исходников (Local Codebase Cache)** — папка `/data/clones/{repo_id}` внутри Docker-контейнера, куда клонируются репозитории для проведения дельта-синхронизации.
* **Автономная синхронизация (Autonomous Sync)** — процесс автоматического обновления семантического индекса и графа символов на основе входящих вебхуков или расписания Cron.
* **Очередь задач (Job Queue)** — таблица `sync_queue` в базе данных SQLite, содержащая упорядоченный список задач на синхронизацию с контролем статусов и количества попыток.
* **Валидатор вебхуков (Webhook Validator)** — модуль криптографической верификации подписей HMAC-SHA256 входящих HTTP-запросов от Git-серверов.
* **OmniRoute** — OpenAI-совместимый локальный API-шлюз/прокси (работает на `http://localhost:20128/v1`), используемый для направления RAG-запросов к модели `kr/claude-sonnet-4.5` с провайдером `kiro`.
* **RAG-чат (RAG Chat)** — диалоговый интерфейс на вкладке Web UI для отправки вопросов к базе знаний и получения ответов со стримингом и списком источников.
* **Идемпотентность задачи (Task Idempotency)** — свойство выполнения задачи синхронизации, при котором повторные запуски для одного и того же коммита/состояния репозитория не приводят к дублированию или порче данных.

## 4. Функциональные возможности (Features)

### 4.1. Надежная фоновая синхронизация на базе БД-очереди
**Описание:** Управление фоновыми задачами синхронизации осуществляется через таблицу очереди в базе данных SQLite. Идемпотентность гарантируется на этапе выполнения воркером, но не гарантируется при добавлении в очередь.

* **FR-1: Хранение очереди в SQLite:**
  * Система сохраняет все запросы на синхронизацию в таблицу `sync_queue`. Поля записи: `id` (INT AUTOINCREMENT), `repo_id` (TEXT), `status` (`pending`, `processing`, `completed`, `failed`), `attempts` (INT, по умолчанию 0), `error_message` (TEXT), `created_at` (TIMESTAMP).
* **FR-2: FIFO обработка воркером:**
  * Фоновый воркер выбирает старейшую запись (`created_at` ASC) в статусе `pending`, переводит её в статус `processing` и начинает выполнение.
* **FR-3: Гарантия идемпотентности при выполнении:**
  * Воркер должен проверять текущий хэш репозитория. Если изменения отсутствуют или задача для данного коммита уже успешно выполнена, индексация завершается без перерасчета векторов.
* **FR-4: Остановка воркера при критической ошибке:**
  * Если задача падает с ошибкой, воркер совершает до 3 попыток перезапуска (`attempts <= 3`) с экспоненциальной задержкой (1-я попытка — через 1 минуту, 2-я — через 5 минут, 3-я — через 15 минут). При превышении лимита воркер помечает задачу как `failed`, записывает текст ошибки в `error_message`, полностью останавливает обработку последующих задач в очереди и переводит статус сервиса в панели Dashboard в состояние `Halted` / `Error`.
* **FR-5: Git-клиент внутри контейнера:**
  * Воркер выполняет клонирование и обновление исходников в папке `/data/clones/{repo_id}`, применяя SSH-ключи (по путям из `config.yaml`) или токен PAT из переменных окружения.

### 4.2. Обработка вебхуков и расписания
**Описание:** Эндпоинты для автоматического приема триггеров от систем контроля версий.

* **FR-6: Криптографическая валидация:**
  * Бэкенд валидирует подпись HMAC-SHA256 для GitHub (`X-Hub-Signature-256`), Gitea (через заголовок `X-Gitea-Signature`) и токен `X-Gitlab-Token` для GitLab. При несовпадении подписи эндпоинт моментально отдает `401 Unauthorized`.
* **FR-7: Cron-планировщик:**
  * Поддержка запуска задач синхронизации по Cron-выражениям, описанным в `config.yaml`.

### 4.3. Панель мониторинга (Web UI Dashboard)
**Описание:** Веб-интерфейс на базе статических файлов без процессов сборки.

* **FR-8: No-Build SPA Фронтенд:**
  * Интерфейс пишется на Vanilla JS/CSS/HTML5 и отдается сервером FastAPI как статические файлы.
* **FR-9: Авторизация Basic Auth:**
  * Защита логином и паролем. При отсутствии установленной переменной `DASHBOARD_PASSWORD` доступ к панели блокируется бэкендом (`403 Forbidden`).
* **FR-10: Отображение очереди задач (Read-Only):**
  * В интерфейс добавляется раздел просмотра очереди задач. Отображаются все задачи, их текущий статус, количество попыток и текст ошибок для упавших задач. Редактирование очереди из UI запрещено.
* **FR-11: Реактивный мониторинг через WebSockets:**
  * Текущие статусы воркера, состояние репозиториев и прогресс-бары синхронизации обновляются на фронтенде в реальном времени через вебсокеты.

### 4.4. Интегрированный RAG-чат
**Описание:** Вкладка чата для формулирования вопросов к базе знаний.

* **FR-12: Чат-интерфейс в браузере:**
  * Текстовое поле ввода, история сообщений, автопрокрутка, рендеринг Markdown ответов LLM с подсветкой синтаксиса кода.
  * **Фича-флаг:** Чат должен быть полностью отключаемым через параметр `server.dashboard.chat.enabled` (true/false) в `config.yaml`. При значении `false` вкладка скрывается, а API эндпоинты чата возвращают `403 Forbidden`.
  * **Память чата:** История диалога хранится в оперативной памяти браузера (на клиенте) и передается при каждом запросе в виде массива сообщений (без хранения истории на бэкенде).
  * **Защита доступа:** Запросы к API чата авторизуются с помощью тех же временных токенов безопасности, что и WebSocket-телеметрия. При несанкционированном доступе возвращается `401 Unauthorized`.
* **FR-13: Гибридный поиск контекста:**
  * Перед отправкой вопроса в LLM система запрашивает `search_chunks_hybrid`, отбирает 5 лучших совпадений и собирает из них контекстный блок системного промпта.
* **FR-14: Совместимость с OmniRoute:**
  * Отправка запросов к локальному прокси-серверу `http://localhost:20128/v1` (OpenAI-совместимый API), модель `kr/claude-sonnet-4.5`, провайдер `kiro`. Токен авторизации берется из переменной `LLM_API_KEY`.
* **FR-15: Посимвольный стриминг:**
  * Бэкенд стримит генерацию текста в реальном времени через Server-Sent Events (SSE) или WebSockets на фронтенд.
* **FR-16: Показ источников:**
  * Блок ссылок под каждым ответом со списком использованных файлов и строчек кода.

## 5. Метрики успеха (Success Metrics)

* **SM-1 (Надежность очереди):** 100% задач из очереди SQLite обрабатываются или помечаются ошибкой. После сбоя питания/контейнера воркер восстанавливает работу и продолжает выполнение с незавершенной задачи.
* **SM-2 (Идемпотентность):** Повторный запуск одной и той же задачи синхронизации занимает <1 секунды и не создает дублирующихся записей или векторов в БД.
* **SM-3 (Качество ответов RAG):** Время начала стриминга ответа в чате через прокси `omniroute` составляет <2 секунд с момента отправки вопроса.

## 6. Открытые вопросы (Open Questions)

1. **Стратегия отмены задач:** Нужна ли кнопка отмены текущей задачи или очистки очереди в Web UI, несмотря на исходное требование Read-Only для очереди? (Решение: на этапе MVP очередь строго Read-Only, отмена задач происходит перезапуском контейнера).
2. **Очистка диска:** Как обрабатывать лимиты дискового пространства в Docker при накоплении кэша `/data/clones` большого количества крупных репозиториев? (Решение: добавить рекомендацию по ограничению максимальной глубины клонирования `git clone --depth 1`).

## 7. Индекс предположений (Assumptions Index)

* **[ASSUMPTION: OmniRoute API]** Локальный прокси `omniroute` полностью поддерживает стандартный JSON-RPC потокенный стриминг OpenAI API (`stream=true`).
* **[ASSUMPTION: SQLite WAL]** Режим WAL в SQLite позволит фоновому воркеру записывать новые чанки и обновлять очередь задач в то время, когда MCP-клиент совершает поисковые запросы по базе.
