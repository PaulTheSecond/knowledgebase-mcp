## Контекст

В соответствии с этапом `v1.6` дорожной карты проекта, системе `knowledge-mcp` требуется простая и функциональная веб-панель управления (Web UI Dashboard). Она необходима для визуального контроля состояния базы знаний, мониторинга запущенных фоновых синхронизаций, просмотра логов ошибок и ручного управления репозиториями без использования консоли или MCP-клиентов.

Панель должна работать внутри того же Docker-контейнера, что и MCP-сервер, потреблять минимум ресурсов и не перегружать финальный образ проекта тяжелыми фронтенд-библиотеками или процессами сборки Node.js.

---

## Проблема

1. **Размер Docker-образа:** Использование современных SPA-фреймворков (React, Angular, Vue) требует сборки (Vite, Webpack), установки сотен npm-пакетов и усложнения пайплайна Docker (multi-stage build с установкой Node.js на этапе выполнения).
2. **Безопасность панели управления:** Доступ к управлению индексацией и логам должен быть защищен, чтобы злоумышленник, получив сетевой доступ к контейнеру, не мог скомпрометировать исходные коды или вызвать отказ в обслуживании (DoS).
3. **Обмен данными в реальном времени:** Процесс индексации может занимать минуты. Классические HTTP-запросы требуют постоянного опроса (polling) для обновления прогресс-бара, что перегружает бэкенд.

---

## Решения

### 1. Легковесный стек без процесса сборки (No-Build Frontend)
Фронтенд панели управления разрабатывается по принципу **No-Build SPA**:
* **Разметка:** Семантический HTML5.
* **Стилизация:** Чистый Vanilla CSS. Используется современная темная тема с эффектами размытия (Glassmorphism), плавными переходами и кастомными шрифтами (например, Inter из Google Fonts).
* **Логика:** Vanilla JavaScript (ES6+), подключаемый напрямую через тег `<script type="module">`.
* **Доставка клиенту:** Статические файлы размещаются в директории `knowledge_mcp/dashboard/static` и раздаются FastAPI-сервером через `FastAPI.mount("/static", StaticFiles(directory="..."))`. Это устраняет необходимость запуска отдельного Node.js-сервера (типа Nginx или Express) в контейнере.

### 2. Схема авторизации и безопасность
* **HTTP Basic Authentication:** Простая, проверенная временем авторизация на стороне сервера. Бэкенд проверяет заголовки `Authorization: Basic ...`.
* **Переменные окружения:** Имя пользователя и пароль задаются на уровне контейнера через `DASHBOARD_USERNAME` (по умолчанию `admin`) и `DASHBOARD_PASSWORD`. Если пароль не задан, доступ к веб-интерфейсу блокируется в целях безопасности (Web UI отдает `403 Forbidden`).
* **Локальный биндинг по умолчанию:** Dashboard по умолчанию слушает только `127.0.0.1`, делая его доступным локально или через настроенный обратный прокси-сервер (Nginx/Traefik).

### 3. API и обновление статусов в реальном времени (WebSockets)
* Вместо частых HTTP-запросов (polling), веб-панель открывает соединение **WebSocket** с бэкендом по адресу `ws://<host>:<port>/ws/status`.
* При изменении статуса синхронизации (например, переход репозитория из `Idle` в `Syncing` или изменение прогресса векторизации) бэкенд мгновенно отправляет JSON-пакет по вебсокету. Фронтенд на лету обновляет прогресс-бар и метрики без перезагрузки страницы.

## Альтернативы и их отклонение

### Вариант А: Использование React/Vite + Docker Multi-stage build
*Отклонено.* React значительно усложняет отладку и поддержку фронтенда для бэкенд-разработчиков. Дополнительное время сборки образа Docker возрастает на 3-5 минут из-за скачивания `node_modules`. Vanilla JS полностью решает текущие задачи отображения списков и графиков при нулевых затратах на сборку.

### Вариант Б: Server-Side Rendering (SSR) через Jinja2 templates
*Отклонено.* Традиционный SSR требует перезагрузки страниц или написания AJAX-скриптов для динамических обновлений. WebSocket-соединение с реактивным обновлением DOM на стороне клиента дает гораздо лучший пользовательский опыт (UX) и не нагружает сервер рендерингом HTML.
