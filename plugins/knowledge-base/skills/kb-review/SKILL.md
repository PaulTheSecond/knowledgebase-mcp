# Knowledge Base Code Review Skill (`kb-review`)

Этот скилл предназначен для проведения сквозного архитектурного и дефектного ревью изменений задачи (ветки) по всем связанным репозиториям проекта (frontend, backend, e2e-tests) с использованием MCP-инструментов базы знаний (`knowledge-mcp`).

## Когда активировать скилл
- Пользователь просит провести ревью: «проведи ревью ветки ORBIT-...», «сделай ревью задачи...», «проверь изменения в feature/ORBIT-.../develop против master».
- Запуск slash-команды `/review` или `/kb-review`.
- Подготовка задачи перед открытием MR или пушем в upstream (например, Норникель).

---

## Шаг 1. Определение параметров ревью

1. **Имя ветки / задачи**:
   - Из запроса пользователя (например, `ORBIT-2045` или `feature/ORBIT-2045/develop`).
   - Если указан только номер задачи `ORBIT-XXXX` — сформируйте каноническое имя ветки `feature/ORBIT-XXXX/develop`.
2. **Целевая ветка (compare_branch)**:
   - По умолчанию `"master"`.
3. **Идентификатор проекта (project_id)**:
   - По умолчанию `"orbita"` (или текущий активный проект воркспейса).

---

## Шаг 2. Вызов инструмента `knowledge_review_context`

Вызовите MCP-инструмент:
```json
{
  "tool": "knowledge_review_context",
  "arguments": {
    "project_id": "orbita",
    "branch": "feature/ORBIT-XXXX/develop",
    "compare_branch": "master"
  }
}
```
> [!NOTE]
> Не передавайте `changed_files` вручную без явной просьбы пользователя: сервер автоматически определит все связанные репозитории (backend, frontend, e2e-tests), вычислит `merge-base` точку ответвления от master и найдет все измененные файлы за 15–25 секунд, отправляя уведомления о прогрессе.

---

## Шаг 3. Анализ ответа по 7 Правилам Регламента

Получив JSON-ответ от сервера, строго соблюдайте следующие правила:

### Правило 1. Только новые дефекты ветки (`origin: "branch"`)
- Сообщайте только о находках, где `origin == "branch"` или `origin == "branch_uncommitted"`.
- Если проблема присутствовала в `master`, это легаси-код — его **запрещено** предъявлять ветке как блокирующее замечание.

### Правило 2. Обязательный аудит всех измененных файлов
- Сверьтесь со списком `reviewed_files`. В итоговом отчёте **каждый** файл диффа должен иметь статус:
  - `clean` (проверен, замечаний нет);
  - `has_findings` (найдены конкретные дефекты).

### Правило 3. Исключение сгенерированного кода
- Файлы `*.Designer.cs`, `.generated.`, `.g.cs` не подлежат ревью и автоматически помечаются как `clean` («Сгенерированный файл, не подлежит ревью»).

### Правило 4. Кросс-репозиторные связки дефектов
- Обращайте внимание на связанные дефекты между бекендом и фронтендом:
  - Стирание имени в SQL-миграции (`B1`) $\leftrightarrow$ отображение устаревшего системного имени на UI (`F4`).
  - Сбор предупреждений Excel-импорта (`F1` в `parseExcelRoutes.ts`) $\leftrightarrow$ скрытие текста в тосте `RouteEditor.tsx`.
  - Фолбэк прав рекрутера (`F3` в `ApprovementAttempt.tsx`) $\leftrightarrow$ отклонение сервером `ApproverMatrixResolver.cs`.

### Правило 5. Транзитивное покрытие E2E-тестами
- Не объявляйте компонент непротестированным (`Test Gap`), если он входит в транзитивное покрытие через родительский сценарий (`e2e_covered_symbols`).

### Правило 6. Прозрачный расчет скоринга риска
- Отразите формулу:
  $$\text{Risk Score} = \min(100, \max(0, \text{Complexity} + \text{BlastRadius} + \text{TestGaps} - \text{Mitigations}))$$

### Правило 7. Точная привязка к коду и чек-листам
- Каждое замечание должно иметь: файл, точные номера строк, краткую суть, степень критичности (`important` / `minor`) и ссылку на пункт чек-листа (`.kb/nn-backend-review-checklist.md`, `.kb/nn-frontend-review-checklist.md`, `.kb/e2e.md`).

## Шаг 4. Формирование стандартизированного отчёта

Сформируйте финальный ответ пользователю по структуре:

### 1. Шапка репозиториев
| Репозиторий | Диапазон коммитов | Кол-во коммитов | Незакоммиченные изменения |
|---|---|---|---|
| backend | sha1..sha2 | N | Нет / Да (файлы) |
| frontend | sha1..sha2 | N | Нет / Да (файлы) |
| e2e-tests | sha1..sha2 | N | Нет / Да (файлы) |

### 2. Сводка по отрецензированным файлам
- Всего файлов на ревью: `X`
- Чистых файлов: `Y`
- Файлов с замечаниями: `Z`

### 3. Таблица находок (только внесенные веткой)
| # | Серьёзность | Репозиторий / Файл : строки | Коммит | Суть замечания | Правило чек-листа |
|---|---|---|---|---|---|

### 4. Радиус влияния и покрытие тестами
- Затронутые компоненты и зависимости (Blast Radius).
- Тесты, покрывающие изменение (unit + E2E).
- Выявленные пробелы (Test Gaps), если они есть.

### 5. Оценка риска и вердикт
- Итоговый Risk Score и уровень риска.
- Рекомендация: готовность к мерджу / пушу в upstream.
